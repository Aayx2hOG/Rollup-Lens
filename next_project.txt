ZK Rollup Learning and Portfolio Plan (Updated)
================================================

Goal
----

Build a practical blockchain infrastructure portfolio that moves from Rust
fundamentals to rollup architecture, Solana indexing, and a final analytics
platform. The goal is not to invent new cryptography. The goal is to prove that
you can build production-shaped systems around signatures, state, indexing,
batching, proofs, APIs, databases, and dashboards.

Recommended final portfolio project:

RollupLens: Solana Rollup Intelligence Platform

It should combine:

- Rust backend services
- Solana RPC ingestion
- PostgreSQL storage
- Real-time indexing
- Wallet, program, token, DEX, and MEV-style analytics
- Explainable wallet and program risk signals
- Transaction timeline and replay views
- Rollup batch simulation from selected indexed activity
- State root tracking and state diff inspection
- Alerts for abnormal activity
- Dashboard and API layer

Guiding Rules
-------------

- Build every project as a real CLI, service, or web app with a README.
- Keep each project small enough to finish, but complete enough to demo.
- Write tests for core logic: signing, proofs, state transitions, indexing, and
  batch execution.
- Prefer Rust for core systems work.
- Prefer boring infrastructure: PostgreSQL, Axum, Tokio, SQLx, React, Docker.
- Standardize on PostgreSQL + SQLx starting at Phase 4 so schema and migration
  patterns carry forward into the indexer and final platform without rework.
- Do not over-focus on advanced ZK math early. First master the systems around
  rollups.
- After each stage, publish a short write-up explaining what was built, what was
  learned, and what tradeoffs were made.


Phase 1: Rust Wallet CLI
------------------------

Time estimate:

3-5 days

Purpose:

Learn keypairs, signatures, serialization, and CLI ergonomics.

Build:

- `wallet create`
- `wallet address`
- `wallet sign <message>`
- `wallet verify <message> <signature> <public_key>`
- Save encrypted or plaintext dev keys locally
- Export/import keys for testing

Recommended stack:

- Rust
- clap
- ed25519-dalek or k256
- serde
- anyhow / thiserror

Acceptance criteria:

- A user can create a keypair and derive an address.
- A user can sign a message and verify it from the CLI.
- Invalid signatures fail cleanly.
- Unit tests cover signing and verification.
- README includes usage examples.

What to learn:

- Public/private keypairs
- Digital signatures
- Message encoding
- CLI design
- Error handling in Rust

Portfolio value:

Small, clean proof that you understand wallet primitives.


Phase 2: Merkle Tree Library and CLI
------------------------------------

Time estimate:

4-7 days

Purpose:

Understand state commitments, Merkle proofs, and how rollups compress state.

Build:

- Rust library for a binary Merkle tree
- `merkle root <file>`
- `merkle prove <file> <index>`
- `merkle verify <leaf> <proof> <root>`
- Support JSON input for leaves
- Print proof paths in a readable format

Recommended stack:

- Rust
- sha2 or blake3
- serde_json
- proptest or quickcheck for property tests

Acceptance criteria:

- Root generation is deterministic.
- Proofs verify for every valid leaf.
- Tampered leaves or proofs fail verification.
- Tests cover empty, one-leaf, odd-leaf, and large-tree cases.
- README explains why Merkle roots matter for rollups.

What to learn:

- Hashing
- State roots
- Inclusion proofs
- Deterministic data encoding
- Property-based testing

Portfolio value:

Important foundational primitive for rollups, light clients, and blockchain
state verification.


Phase 3: Minimal Blockchain From Scratch
----------------------------------------

Time estimate:

1-2 weeks

Purpose:

Learn blocks, transactions, balances, nonces, state transitions, and chain
validation.

Build:

- Account model with balances and nonces
- Signed transactions
- Blocks containing transactions
- Block hash and parent hash
- State transition function
- Chain validation
- CLI commands:
  - `chain init`
  - `chain account create`
  - `chain tx send`
  - `chain block produce`
  - `chain validate`

Recommended stack:

- Rust
- sled or plain JSON files for local persistence
- serde
- tracing

Acceptance criteria:

- Invalid signatures are rejected.
- Double-spend attempts fail.
- Nonce replay fails.
- Blocks link correctly by parent hash.
- Full chain validation can rebuild state from genesis.

What to learn:

- State machines
- Transaction validity
- Block structure
- Replay protection
- Deterministic execution

Portfolio value:

Shows that you understand the execution layer beneath blockchains and rollups.

Phase 5: Solana Indexer
-----------------------

Time estimate:

2-3 weeks

Purpose:

Move from toy chains to real blockchain infrastructure.

Build:

- Ingest Solana slots, blocks, transactions, accounts, and program activity
- Track configured wallets and programs
- Store indexed data in PostgreSQL
- Provide query APIs for:
  - Recent transactions
  - Wallet activity
  - Program activity
  - Token transfers
  - Failed transactions
- Add backfill and live indexing modes

Recommended stack:

- Rust
- Tokio
- Axum
- SQLx
- PostgreSQL
- Solana RPC
- Docker Compose

RPC considerations:

- Public RPC endpoints rate-limit aggressively; decide early whether to use a
  paid provider (e.g. Helius, QuickNode, Triton) or a free tier with strict
  backoff and request batching.
- Budget indexing scope (slot range, number of tracked wallets/programs) to
  fit within the chosen provider's limits before writing ingestion logic.

Optional later:

- Kafka or Redpanda for event streaming
- ClickHouse for analytics-heavy queries
- Geyser plugin integration

Acceptance criteria:

- Indexer can backfill a selected slot range.
- Indexer can follow new slots continuously.
- Database schema supports wallets, transactions, instructions, programs, and
  token transfers.
- API can answer common wallet and program queries.
- Failed RPC calls retry with backoff.
- Progress is resumable after restart.
- Integration tests cover backfill, live indexing, and resume-after-restart
  behavior using recorded or mocked RPC responses.

What to learn:

- Solana transaction structure
- RPC limitations
- Data ingestion pipelines
- Idempotent writes
- Database indexing
- Operational reliability

Portfolio value:

Very high. This is close to real infrastructure work used by exchanges,
analytics platforms, wallets, and protocol teams.


Phase 6: Rollup Simulator
-------------------------

Time estimate:

2 weeks

Purpose:

Understand rollup architecture without getting blocked by production-grade
settlement or cryptography.

Build:

Flow:

Users -> Sequencer -> Batch -> State Transition -> State Root -> Settlement Log

Features:

- Users submit signed transactions.
- Sequencer orders transactions.
- Batch builder groups transactions.
- Executor applies transactions to state.
- Merkle root commits to the new state.
- Settlement module records batch metadata.
- Explorer shows batches, state roots, and included transactions.
- Batch status field includes at least: pending, finalized (this anticipates
  Phase 7's challenge states so the schema doesn't need to change later).

Recommended stack:

- Rust
- Axum
- PostgreSQL
- Existing Merkle library from Phase 2
- Existing wallet/signature code from Phase 1

Acceptance criteria:

- A batch can be built from pending transactions.
- State root changes deterministically after execution.
- Invalid transactions are excluded or marked failed.
- Batch metadata includes previous root, new root, tx count, and timestamp.
- A user can query which batch included their transaction.

What to learn:

- Sequencing
- Batching
- State commitments
- Rollup data flow
- Separation between execution and settlement

Portfolio value:

This becomes the bridge between blockchain fundamentals and rollup-specific
systems.


Phase 7: Optimistic Rollup Mechanics (Optional / Time-Permitting)
------------------------------------------------------------------

Time estimate:

2 weeks

Status:

Optional. This phase deepens conceptual understanding of fraud proofs and
challenge periods, but its output is not required by Phase 9's MVP. If time is
short, skip this phase and go straight to Phase 8 or Phase 9. If included,
the batch status values it adds (challenged, rejected) extend the
pending/finalized states already defined in Phase 6, so no rework is needed.

Purpose:

Learn fraud proofs and challenge periods conceptually through a working
simulation.

Build:

- Challenge window for submitted batches
- Watcher/verifier service
- Fraud proof for an invalid state transition
- Batch status:
  - pending
  - finalized
  - challenged
  - rejected
- Simple dispute flow that re-executes a disputed transaction or batch

Acceptance criteria:

- Valid batches finalize after the challenge window.
- Invalid batches can be challenged.
- A challenge can prove expected state does not match claimed state.
- Rejected batches are not treated as finalized.
- Tests cover valid finalization and invalid-batch challenge flows.

What to learn:

- Optimistic assumptions
- Fraud proofs
- Challenge windows
- Watcher responsibilities
- Finality tradeoffs

Portfolio value:

Shows that you understand the architecture behind Optimism and Arbitrum-style
systems, even if the implementation is intentionally simplified.


Phase 8: zkVM Experiment
------------------------

Time estimate:

1-2 weeks

Purpose:

Add practical ZK exposure using existing zkVM tooling instead of writing
cryptography from scratch.

Choose one:

- SP1
- RISC Zero

Build:

- A guest program that executes the *same state transition function used by
  the Phase 6 rollup-simulator* (not a toy/unrelated example), so the proof
  is directly reusable as a Phase 9 stretch goal.
- Public inputs:
  - previous state root
  - new state root
  - batch commitment
- Private or committed inputs:
  - transactions
  - account state
- Host program that generates and verifies a proof.

Acceptance criteria:

- A valid batch execution (using real or representative data from the
  rollup-simulator) produces a proof.
- The verifier accepts the proof.
- Tampered public inputs fail verification.
- README explains what is proven and what is not proven, and how this guest
  program maps to the rollup-simulator's executor.

What to learn:

- zkVM host/guest model
- Public inputs
- Proof generation
- Verification
- Practical constraints of proving execution

Portfolio value:

Strong signal that you can work with modern ZK tooling pragmatically.


Phase 9: Final Portfolio Project
--------------------------------

Project:

RollupLens: Solana Rollup Intelligence Platform

Time estimate:

8-10 weeks for a strong version (this absorbs Phases 6-8's remaining work;
the original 4-6 week estimate assumed Phases 6-8 were already complete
standalone projects, which is unrealistic if folded in incrementally)

Purpose:

Create one polished project that combines the strongest parts of the previous
work into something useful, demoable, and credible. The project should not feel
like a generic blockchain dashboard. It should act like an investigation and
simulation tool: ingest real Solana activity, explain wallet and program
behavior, surface suspicious patterns, and let users turn selected activity into
a simulated rollup batch with state-root tracking.

Product positioning:

Inspect Solana activity, detect wallet and program patterns, and simulate
rollup batches with state-root tracking.

Core workflow:

Solana RPC -> Indexer -> Analytics -> Select Transactions -> Rollup Batch ->
State Transition -> State Root -> API/Dashboard

Core features:

- Real-time Solana transaction ingestion
- Wallet activity analytics
- Program activity analytics
- Token and DEX activity tracking
- Failed transaction and error analysis
- Basic MEV-style and bot-pattern detection
- Explainable wallet/program risk score
- Transaction timeline for wallets and programs
- Replay mode for recent wallet/program activity
- Rollup "what if" batch simulator
- State root tracking
- State diff viewer for simulated batches
- Merkle proof lookup for accounts or batch entries
- Alerts for abnormal wallet, program, token, or batch behavior
- API for indexed and simulated rollup data
- Dashboard for wallets, programs, transactions, batches, and alerts

Differentiating features:

- From Solana stream to simulated rollup batch:
  Users can select real indexed Solana transactions and simulate how they would
  be grouped, executed, accepted/rejected, and committed inside a rollup-style
  batch.

- Explainable risk signals:
  Wallet and program views should show why an address looks normal or
  suspicious. The score must be transparent, not a black box.

- Investigation timeline:
  Wallet and program pages should show activity over time: transfers, swaps,
  failed transactions, program calls, large balance changes, alerts, and batch
  inclusion events.

- Replay mode:
  A demo-friendly mode that replays a wallet or program's activity slot by slot,
  with metrics and alerts updating as the timeline advances.

- State diff and root tracking:
  Rollup simulation should show previous state root, new state root, included
  transactions, rejected transactions, and account-level balance/state changes.

Suggested architecture:

- `indexer-service`
  - Reads Solana RPC
  - Backfills historical slots
  - Streams live transactions
  - Writes normalized records to PostgreSQL

- `analytics-service`
  - Computes wallet metrics
  - Computes explainable wallet and program risk scores
  - Detects high-frequency activity
  - Detects failed transaction spikes
  - Detects simple sandwich-like or arbitrage-like patterns
  - Detects repeated DEX activity, bot-like bursts, and abnormal token movement
  - Produces alert records for dashboard and API consumers

- `rollup-simulator`
  - Accepts selected Solana-like transactions or simplified internal transfers
  - Builds batches
  - Executes state transitions
  - Produces state roots
  - Produces account/state diffs for each simulated batch
  - Marks transactions as accepted, rejected, or failed with explicit reasons
  - Exposes Merkle proofs for account or transaction inclusion when supported
  - Exposes batch status (including challenge states if Phase 7 was completed)

- `api-service`
  - Axum API
  - Serves wallet, program, transaction, analytics, and rollup endpoints

- `dashboard`
  - React frontend
  - Analytics overview
  - Wallet view
  - Program view
  - Transaction explorer
  - Timeline/replay view
  - Batch explorer
  - State diff viewer
  - Alert center

- `database`
  - PostgreSQL
  - Migrations
  - Indexes for slot, signature, wallet, program, mint, and timestamp

Minimum viable demo:

- Backfill recent Solana transactions for a configured wallet or program.
- Display transactions in a dashboard.
- Show basic wallet analytics and an explainable risk score.
- Show a transaction timeline for the configured wallet or program.
- Build a simulated rollup batch from selected transactions.
- Show accepted/rejected transactions, previous state root, new state root,
  batch contents, and state diffs.
- Show at least one alert, such as a failed transaction spike or high-frequency
  activity burst.
- Expose all important data through an API.

Stretch goals:

- WebSocket live updates
- Timeline replay mode with slot-by-slot playback
- Kafka or Redpanda event bus
- ClickHouse analytics store
- zkVM proof for simulated batch execution (using the Phase 8 guest program)
- Alerting for abnormal wallet or program behavior
- Configurable watchlists for wallets, programs, mints, and DEX programs
- Public demo mode with recorded Solana RPC fixtures
- Public hosted demo
- Benchmarks for ingestion throughput

Acceptance criteria:

- Project starts with Docker Compose.
- README has a clear architecture diagram and setup instructions.
- Demo seed data is available if Solana RPC rate limits are hit.
- Backend services have integration tests.
- Risk-score heuristics are documented and tested against fixture data.
- Rollup simulation tests cover accepted, rejected, and failed transactions.
- Core analytics queries are indexed and reasonably fast.
- Dashboard works on desktop and mobile widths.
- A 3-5 minute demo video can explain the full system.

Demo story:

1. Track a configured Solana wallet or program.
2. Backfill recent activity and show the timeline.
3. Explain the wallet/program risk score and alert signals.
4. Select interesting transactions and simulate a rollup batch.
5. Show accepted/rejected transactions, state diffs, and the new state root.
6. Use the API to fetch the same wallet, analytics, alert, and batch data.

Why this is the best final project:

- It avoids pretending to build a production L2 from scratch.
- It demonstrates real Rust and blockchain infrastructure ability.
- It connects Solana, data engineering, analytics, and rollup concepts.
- It is more distinctive than a plain indexer because it connects live chain
  data to rollup simulation, risk scoring, state diffs, and replay.
- It is understandable to recruiters, protocol teams, and infra teams.
- It creates multiple talking points: indexing, state roots, batching,
  transaction analysis, APIs, databases, alerts, replay, and distributed
  systems.

Repository Structure Recommendation
-----------------------------------

Use a single workspace so projects can share code:

- `crates/wallet-core`
- `crates/merkle`
- `crates/chain-core`
- `crates/rollup-core`
- `apps/wallet-cli`
- `apps/merkle-cli`
- `apps/mini-chain`
- `apps/explorer-api`
- `apps/solana-indexer`
- `apps/rollup-simulator`
- `apps/dashboard`
- `migrations`
- `docs`

Shared crates should hold reusable logic. Apps should contain binaries,
services, and UI-specific code.

Add crates incrementally as each phase introduces them rather than scaffolding
all of them upfront — e.g. `crates/rollup-core` is created in Phase 6, not
before. This avoids empty-crate clutter early on.
